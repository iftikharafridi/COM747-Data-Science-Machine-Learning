Data Analytics and Data Engineering

01

Where is the money going?

A large Irish oil company uses tanker drivers to deliver oil all over Ireland. Profits are much lower than expected and they think they are losing money somehow. They hand their data to an investigative analytics team at a consultancy and ask: what is happening with our money?

The team doesn't start by running models. It starts with hypotheses ("one or more drivers are using the trucks for their own use and claiming back the fuel") and with careful data work: load it, check it, join it, aggregate it, and present the evidence. That is most of real-world data science.

  • LO2Explain the load → validate → transform → present process and the ETL pipeline.

02

Three data roles

Investigative analyst

Consultancy work: one-off investigations (fraud, disputes, compliance). Loads raw client data into SQL Server or Alteryx, tests hypotheses, presents findings in PowerPoint or Tableau. Excel and PowerPoint skills matter.

Data analyst

Repeated analysis of data that keeps arriving, e.g. quarterly Medicare data on lung cancer and lab data on biomarker testing (EGFR), cleaned in a KNIME workflow, turned into graphs and recommendations with a domain expert.

Data engineer

Builds the pipelines that make data available and consumable: Extract, Transform, Load (ETL) with SQL and Python, cloud infrastructure, triggers and checks, so analysts and applications always get clean data.

The roles overlap with each other and with cloud and software engineering, so read job descriptions carefully. A common path: maths or computing degree → analyst → engineer. You pick up the domain (insurance, medicine, oil) faster than you expect.

04

Validate: is the data loaded the data sent?

Before any analysis, check that nothing was lost or changed on the way in. Compare simple fingerprints of the file the client sent with the table you loaded: column count, row count, and max / min / sum of the numeric columns. They are cheap to compute and catch most load errors.

Explorer

Break the load and see which check catches it

Source: 480 made-up diesel claims (driver, date, litres, amount in €). Each fault changes some fingerprints but not others, which is why we check several.

sent   <- read.csv("diesel_claims.csv")          # what the client says they sent
loaded <- dbGetQuery(con, "SELECT * FROM diesel_claims")   # or the data frame you loaded

c(ncol(sent), ncol(loaded))                       # column counts
c(nrow(sent), nrow(loaded))                       # row counts
sapply(list(sent = sent$amount, loaded = loaded$amount),
       function(x) c(min = min(x), max = max(x), sum = sum(x)))
stopifnot(nrow(sent) == nrow(loaded), all.equal(sum(sent$amount), sum(loaded$amount)))
05

Transform: joining log books and diesel claims

Three sources: scanned log books (when each driver checked in and out), employee details, and diesel claims. The names in the scanned log books were messy, so they were cleansed first (cleansed_name). Then the key step: join log books to claims on driver and date.

SELECT lb.cleansed_name, lb.date, lb.duration, dc.diesel_claims
FROM log_books_table lb
JOIN diesel_claims_table dc ON lb.cleansed_name = dc.driver AND lb.date = dc.date

06

Present: telling the story

Aggregate the joined data per driver: total hours driven against total fuel claimed. If fuel is roughly proportional to driving, one line fits everyone, and a driver far above it needs explaining. A clear chart is the deliverable, not the SQL.

Evidence, not proof. An outlier is a lead for investigation (maybe that driver's truck is older, or their log book scans failed), not a conclusion. Present it with its caveats.
07

The data engineer: ETL pipelines

Analysts often load data by hand once. Engineers make it repeatable. Case: insurance claim specialists need medical codes (ICD-10, e.g. C34 for lung cancer) on every claim. A paid lookup tool was so awkward that staff googled codes instead (inaccurate, not repeatable). The engineering team built an internal database and simple search instead: Extract the raw code files, Transform them into a lookup table, Load them into a cloud database behind an API.

Explorer

A few real ICD-10 category codes. In R this search is subset(icd, grepl("lung", description, ignore.case = TRUE)); in SQL it's WHERE description LIKE '%lung%'.

Inside the black box: one neuron

A neuron takes a weighted sum of its inputs plus a bias, then squashes it with an activation function, usually the logistic sigmoid (the same curve as logistic regression in Week 6): output = σ(w₁x₁ + w₂x₂ + b). One neuron draws one straight line through the data. A network stacks many neurons in layers, so it can bend the boundary; training (backpropagation, as in Week 7's gradient descent) adjusts all the weights to reduce the error.

Key terms

TermMeaning
Data validationChecking the loaded data matches the source: column and row counts, min/max/sum.
JOINCombine tables on matching keys. INNER keeps matches; LEFT/RIGHT keep all of one side; FULL keeps all.
Anti-joinRows in one table with no match in the other.
ETLExtract, Transform, Load: the data engineer's pipeline.
Landing zoneWhere raw deliveries arrive before processing.
NeuronWeighted sum of inputs plus bias, passed through an activation function.
Hidden layerNeurons between inputs and outputs; more neurons allow more complex boundaries.
BackpropagationGradient descent for networks: passes the error backwards to update every weight.
Black boxA model whose reasoning is hard to extract (neural networks, SVMs).
